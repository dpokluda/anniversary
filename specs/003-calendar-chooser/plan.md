# Implementation Plan: Calendar Chooser

**Branch**: `003-calendar-chooser` | **Date**: 2026-10-09 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/003-calendar-chooser/spec.md`

## Summary

Let the user choose the name-day calendar, and ship calendars for more countries. Each calendar stays a separate JSON
file, `Anniversary.Calendar.*.json`, found next to the executable, in the app-data folder and among the calendars
embedded in the app, merged by file name with the same precedence as every other file. `AnniversaryBook` discovers them
(`Calendars`, `RefreshCalendars()`), applies the remembered choice when it loads (`Load(preferredCalendar, …)`) and
switches without touching the people (`UseCalendar()`); `CalendarData` gets the optional metadata `name`, `locale`,
`source` and `license`, and a small record, `CalendarInfo`, describes one entry of the menu. The ⋯ menu gets a **Nameday
Calendar** submenu of radio items (on macOS also under **View**), rebuilt each time the menu opens; the choice is saved
as `calendar` in `usersettings.json`. Ten calendars ship: v4's Czech calendar and nine generated by
`calendars/Build-Calendars.ps1` from pinned, openly licensed sources (radoone/nameday-mcp, MIT; the Latvian State
Language Centre's list, CC0), documented in `calendars/README.md`, with `calendars/THIRD-PARTY-NOTICES.md` copied next
to the executable.

## Technical Context

**Language/Version**: C# (latest) on .NET 10 (`net10.0`); PowerShell 7 for the calendar generator

**Primary Dependencies**: Avalonia 12.1.4 with the Fluent theme: the commands `MenuFlyout` with radio `MenuItem`s, and
for the macOS menu bar a `NativeMenu` with radio `NativeMenuItem`s; `System.Text.Json` (case-insensitive, comments and
trailing commas allowed) for the calendar files and `usersettings.json`. No new packages. The generator needs no
modules: it uses PowerShell's built-in cmdlets (`Invoke-WebRequest`, `ConvertFrom-Json -AsHashtable`,
`ConvertFrom-Csv`) and .NET classes.

**Storage**: JSON files. The calendars are read-only for the app: the files in `calendars/`, embedded in
`Anniversary.Shared`, plus any user files next to the executable or in the app-data folder. `usersettings.json` in the
app-data folder gets the key `calendar`; the read-only `appsettings.json` still names a calendar with `calendarFile`
(default `Anniversary.Calendar.Czech.json`).

**Testing**: xUnit v3 via Microsoft.Testing.Platform (`dotnet test --project Anniversary.Tests`), classic style with
real files in `TempFolder`s and the embedded calendars; 10 test cases in `Anniversary.Tests/CalendarTests.cs` (78 tests
in total at the move to GitHub); the menus are checked by hand ([quickstart.md](quickstart.md)). The generator validates
its own output, and a second run showed that it reproduces the files.

**Target Platform**: Windows (x64), macOS (arm64 and x64) and Linux (x64) desktops, the phase-1 publish targets
(`win-arm64` and `linux-arm64` came with [005](../005-ci-pipeline/spec.md))

**Project Type**: desktop app

**Performance Goals**: no background work. Each time the commands menu opens, the app reads and parses every calendar
file it finds (the ten embedded ones plus the user's) to list them; switching reads one file of at most 366 short
entries.

**Constraints**: name days are never typed in or made up by hand; only pinned, openly licensed sources (or v4's own
Czech calendar); v4 calendar files must still load, so all metadata is optional; the app never writes calendar files or
`appsettings.json`; day keys stay v4's fixed `MM-dd`; the license notices must ship next to the executable.

**Scale/Scope**: ten shipped calendars of 362 to 366 days; one submenu in the ⋯ menu and one in the macOS View menu; one
new record (`CalendarInfo`); on `AnniversaryBook` the `preferredCalendar` parameter of `Load`, `Calendars`,
`CalendarFile`, `RefreshCalendars()` and `UseCalendar()`; `UserSettings.Calendar`; four optional `CalendarData`
properties.

**Structure Decision**: The existing three-project layout is kept. The logic goes into `AnniversaryBook` and the menus
into the existing `MainWindow`; the only new code file is the `CalendarInfo` record. The calendar data gets a top-level
`calendars/` folder with its generator, README and notices (spec 4), and the projects link the files from there:
`Anniversary.Shared` embeds the calendars and `Anniversary.Desktop` copies the notices. The generated files are kept, so
building the app never needs the generator.

## Complexity Tracking

| Violation | Why Needed | Simpler Alternative Rejected Because |
|---|---|---|
| New type `CalendarInfo` (`Anniversary.Shared/CalendarInfo.cs`, a record of three values) | The menu lists every available calendar and needs, for each, the file name to switch to and remember, the name to show, and the locale (kept for a later automatic choice), without keeping every calendar's days | `CalendarData` describes a file's content: it holds a whole year of names and has no file name, so it can't stand for a menu entry on its own |
